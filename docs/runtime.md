# The runtime (roadmap step 3)

Last updated 2026-11-19 (v0.15.0: the game runs: AX lifted over a native DSP and audio DMA, saves on a host folder, safe points in lifted loops; it initialises, reaches its title scene and keeps running a frame per retrace. v0.14.0: GX's CPU side, VI. v0.13.0: the OS's threads and alarms, DVD. v0.12.0: the skeleton).

## Where bring-up stands (v0.15.0)

The game **initialises completely** (`Init Process Took … msecs`, its own report), saves on first boot (`Riq.dat` and its banner), runs its opening scenes, changes to its **title scene**, and **keeps running**: in a 40-second run, 2,383 frames copied out for 2,397 retraces, 45,401 draws, 13,307 audio frames (332.7 a second, the console's 333.3), no periodic interrupt dropped, 12 threads. Nothing is drawn on screen yet (the GX sink is headless) and nothing sounds (no voice has played: the DSP stops when one does), and with no remote connected the game waits at its title. Use `QILIN_RUN_SECONDS` for runs like these.

Next: **the Vulkan renderer** for GX, now that the game draws every frame; **the mixer** (the DSP stops at the first voice); **input** (a host backend for the Wii Remote).

## Diagnostics

- **Counters** with every stop, and with `QILIN_RUN_SECONDS=N` (which ends the run after N seconds, exit status 3): thread switches and threads started, interrupts (decrementer), files and bytes read, draws and vertices, frames copied out, retraces, audio frames, **periodic interrupts dropped** (an audio frame lost is music running slow), and where deliveries happened (idle, running code).
- **A guest call stack** with every stop: the stack frames' back chain and saved return addresses, from the running thread's registers as last synced.
- **Every guest thread** at the time limit: its state, priority, queue and call stack, and the scheduler's state (current thread, run-queue bits, reschedule count). This is how the loop-poll problem below was found.
- **The game's own reports** (`OSReport`, MSL's `printf`): `OSReport` is lifted and formats through MSL; MSL's console writes to the debug UART, which here goes to stderr prefixed `[game]`, as a development kit's serial port shows it. A deliberate difference from retail, where the UART isn't there; the only effect the game could see is `printf`'s return value, which `OSReport` ignores. (MSL also calls the debugger stub's console write on every console: on retail it reads the stub's "serial I/O" byte, 0, and returns; lifted as such.)

## Building and running

The runtime has its own lift, next to the differential test's. The test lifts every library, to check the lifter on as much code as possible. The runtime's lift (`--runtime`) turns the functions of replaced and dropped libraries (`code-analysis.md`) into calls to native code, except the units and functions the plan lifts out of them.

```sh
python3 tools/analysis/port_symbols.py --qilin build/qilin --dol path/to/main.dol --symbols-out pal_symbols.txt
build/qilin lift path/to/main.dol --out gen-rt --runtime --symbols pal_symbols.txt
cmake -S . -B build-rt -DQILIN_RUNTIME_GEN_DIR=$PWD/gen-rt && cmake --build build-rt --target qilin_run --parallel
build-rt/qilin_run path/to/extracted-disc       # the folder Dolphin's Extract Entire Disc wrote
```

`qilin_run` takes the **extracted disc's folder** (`sys/main.dol`, `sys/fst.bin`, `files/`): Dolphin → right-click the game → Properties → Filesystem → right-click the disc → **Extract Entire Disc**. The `.wbfs` or `.iso` can't be read directly: a Wii disc is encrypted with a key this project can't include, and the extraction writes the files decrypted. Given `main.dol` alone, it runs until the game first touches the disc.

`pal_symbols.txt`, `gen-rt/` and the extracted disc are derived from the game: never commit them (`gen-rt/` and `pal_symbols.txt` are gitignored; keep the disc outside the repository). Exit status: 0 the game ended itself, 1 it stopped, 2 the runtime couldn't start.

When it stops, `qilin_run` says what it has done so far (thread switches, threads started, interrupts delivered, files opened, bytes read), so a run shows which parts of the runtime it exercised, then why it stopped.

## How replaced code is reached

- **`qilin lift --runtime`** (`recomp/src/main.cpp`, the plan in `recomp/src/libraries.*`): a function in a replaced or dropped library becomes `rt::native(c, index)`, and `natives.cpp` lists them (address, name, library). `symbols.cpp` lists every function's name, for reports and for the functions the runtime calls by name. Because these stand in the function table like any other function, direct calls, tail calls and calls through pointers all arrive the same way.
- **Lifted out of replaced libraries** (`libraries.cpp`): whole translation units by name (`kLiftUnits`), single functions by name (`kLiftAnyway`), and exceptions inside a lifted unit that stay native (`kNativeAnyway`). Names, not addresses, so the repository keeps no list of PAL addresses. The lift fails if a name in the plan isn't in the symbol list.
- **The registry** (`recomp/runtime/native.*`): native code registers by the decomp's function name, `QILIN_NATIVE(OSGetTick) { ... }`. At start-up `bind_natives()` joins registrations to the generated table and refuses to start if a registered name isn't a replaced function of the game, is ambiguous, or is registered twice.
- **Names checked against code:** a native whose name could sit on the wrong function states the instructions it expects, `QILIN_NATIVE_CODE(PPCMtdec, 0x7C7603A6u, 0x4E800020u)` (`mtspr DEC, r3; blr`), and `qilin_run` refuses to start if the function of that name doesn't have them. This guards against what v0.13.0 found: in a run of equal-size functions, size alignment had put eight names of the base library three functions early, `PPCMtdec` on the function that writes HID0 (`code-analysis.md`; `port_symbols.py` now checks accessor names against their code).
- **Fail loudly:** a replaced function without native code stops the game when it is called (`Stop::Unregistered`), and `qilin_run` names it, its library and its caller:
  `stopped: no native code yet for 800FD630 (GXInit) [gx], called from 801D7C98 (__ct__15CGraphicManager…+0x9C)`.
  The same report covers the other stops: an access outside the memory lifted code may use, an indirect call to something that isn't a function, a return to the wrong place, a trap, a function that isn't lifted, and a game no thread of which can run (`Stop::Idle`).

## Start-up

`qilin_run` (`recomp/runtime/run.cpp`) does what `__start` does in the supported build (`dol-analysis.md`), without lifting it:

1. Loads the DOL into MEM1 (24 MB at `0x80000000`); MEM2 (64 MB at `0x90000000`) is zeroed. The rest of the 4 GB guest space is reserved and inaccessible. Then binds the natives (after loading: some check the code they replace).
2. Sets the registers `__init_registers` and `__init_hardware` set: the stack pointer with `__start`'s terminating frame, the small-data bases, HID2 with paired singles and quantised loads enabled. Reads `SelectThread`'s globals from its code (below).
3. Calls `OSInit` (native), `__init_user` (lifted: the static constructors), `main(0, 0)` (lifted), then `exit` (lifted: the static destructors, then `PPCHalt`, native, which ends the run with status 0). Each call has the link register `__start` would give it.

`OSInit` sets the arenas, writes the bus and CPU clocks to low memory (the SDK's tick conversions read them: 243 MHz and 729 MHz), runs the lifted units' initialisers in its own order (`__OSInitAlarm`, then `__OSThreadInit`) and turns interrupts on.

`__start`'s other steps aren't needed: `__init_data` copies sections onto themselves and the loader leaves BSS zeroed; the debugger checks are for development kits; and the disc passes no arguments.

**Bring-up runs with checked memory.** Lifted code may use MEM1, low memory included (the lifted OS keeps its globals there), and MEM2. The uncached mirrors and the hardware registers stop with the address and the instruction, so each one lifted code really uses is found and then provided on purpose. Native code reads and writes guest memory unchecked.

## Threads

Agreed with the owner on 2026-11-18: the OS's software is lifted, and only what is under it is native.

- **Lifted units** (`kLiftUnits`): `OSThread.c`, `OSMutex.c`, `OSMessage.c`, `OSTime.c`, `OSAlarm.c`, `OSAlloc.c` (the OS heap allocator, lists in arena memory). None has a privileged instruction. The SDK's own code decides which thread runs and when an alarm fires, with its priorities and queues exactly. From `OSContext.c`, `OSClearContext`, `OSGetCurrentContext` and `OSGetStackPointer` are lifted too.
- **`SelectThread` is native** (`recomp/runtime/threads.cpp`), following the build's own code step by step: run queues, the bitmask of non-empty queues, the reschedule flag, the switch callback, the idle context. Lifted, its idle loop would spin forever, waiting in a loop with no call in it for an interrupt to make a thread ready. Only its context save and load differ: each guest thread runs on its own host thread, which keeps the guest registers in its own `rt::Context`, and a switch hands a run token to the next thread's host thread and waits for its own turn. One guest thread runs at a time, as on the Wii's single core. Host threads rather than fibres or stack switching, to keep the runtime free of platform assembly. Each of those host threads (the first guest thread's too) has an 8 MB stack of its own on every system (`start_guest_thread`, `kGuestStackBytes` in `machine.hpp`), as lifted calls nest as deeply as the guest's: `std::thread` would take the system's default, 512 KB for a secondary thread on macOS.
- **Its globals come from its own instructions** at start-up (eight D-form instructions at known offsets: the small-data offsets from `r13` and two `lis`/`addi` pairs). If they aren't where the supported build has them, `qilin_run` refuses to start.
- **A new thread** starts on its own host thread the first time it is chosen, with the registers `OSCreateThread` left in its context and the interrupt enable its saved MSR gives it, at its entry point; when the entry returns, it goes on into `OSExitThread`, as the link register `OSCreateThread` set sends it. A thread that has exited ends its host thread when it switches away. `OSInitContext` is native so that a thread structure reused for a new thread retires the host thread still waiting on the old one.
- **Idle:** with no thread ready, the scheduler waits for the next interrupt and delivers it, until one makes a thread ready, as the original's idle loop does. If nothing could ever arrive (no alarm set, nothing queued), the game is stuck and stops (`Stop::Idle`), naming the thread that went to sleep last.

OSThread's layout, from the code: the saved context at +0 (GPRs, CR +128, LR +132, CTR +136, XER +140, FPRs +144, SRR0 +408, SRR1 +412, state +418, GQRs +420, ps1 +456), state +712 (1 ready, 2 running, 4 waiting, 8 moribund), priority +720, queue +732, links +736/+740, stack +772/+776. Low memory: current context `0x800000D4`, FPU context `0x800000D8`, active threads `0x800000DC`/`0x800000E0`, current thread `0x800000E4`.

## Interrupts and alarms (`recomp/runtime/interrupts.*`)

The Wii raises an interrupt between any two instructions; lifted code can't be entered there, so the runtime delivers interrupts at **safe points**, where the guest's stack pointer is known (handlers build their frames below it):

- when the game enables interrupts (`OSEnableInterrupts`, or `OSRestoreInterrupts` turning them on);
- **at every call into native code** (v0.15.0): the lifted caller has just stored the registers it changed, `r1` among them;
- **on every backward branch of lifted code** (v0.15.0), so a loop that waits for an interrupt gets it, as on the console. The lifter emits `if (rt::poll_due()) [[unlikely]] { c.r[1] = r1; rt::poll(c); }`: a flag test while an interrupt is queued, and a look at the clock every 1,024th time round for the timers. Found when the Mii library spun in `RFLInitRes` (a loop with no call in it) waiting for a NAND callback. 2,594 polls in the runtime's lift; in the differential test `rt::poll` does nothing;
- and while the scheduler is idle.

A delivery saves the whole context and puts it back, so the interrupted function's live registers (host locals) and the context agree again afterwards; delivery state is per host thread, so a switch during a delivery's reschedule leaves the next thread free to take interrupts. Interrupts are only delivered while enabled.

**Periodic interrupts catch up** (v0.15.0): when delivery comes late, each period that has passed runs in turn, as the console takes every audio DMA and every retrace; only a stall of more than 32 periods (about 100 ms of audio) drops the rest, counted. **Windows** rounds short waits up to its 15.6 ms tick: `qilin_run` asks for 1 ms timers (`timeBeginPeriod`) so the idle wait wakes for each 3 ms audio frame. Before both fixes, 80% of audio frames were lost (one per retrace instead of one per 3 ms).

**I/O completions take time** (v0.15.0): queued interrupts have a due time, and DVD and NAND completions arrive no sooner than 1 ms after the request. On a console a request takes milliseconds, and the game sets its "loading" flag after issuing one (`loadFile`: `DVDReadAsyncPrio`, then the flag; the callback clears it); a completion delivered at once, at the next safe point, cleared the flag before it was set and left `waitDVD` waiting forever. Disc speed itself isn't modelled: reads finish far sooner than on a console.

- **A queued interrupt** (a DVD completion, later VI and audio) runs as the SDK's dispatcher runs a handler: `OSDisableScheduler` (so a thread woken inside it doesn't switch there), the handler, `OSEnableScheduler`, `__OSReschedule` (which may switch threads). The three are lifted code.
- **The decrementer** runs the handler the OS installed for it (`__OSSetExceptionHandler`, native: the runtime keeps the table) with the interrupted context. `PPCMtdec` sets the deadline on the time base, as the alarm code's `InsertAlarm` asks. The SDK's decrementer callback then fires the due alarms and ends in `OSLoadContext`, which on the console never returns: natively it unwinds back to the delivery, which puts the interrupted registers back. Anywhere else `OSLoadContext` stops the game: it would be a context switch the runtime doesn't make.
- **Every register** is as the interrupted code left it after a delivery. Delivery state belongs to the host thread delivering, so a switch during the reschedule leaves the next thread free to take interrupts.

## DVD (`recomp/runtime/dvd.*`)

The disc's own file table (`sys/fst.bin`) gives the entry numbers and directories, so they are the console's; the contents come from `files/`. Lookup follows the SDK: from the root (nothing the game lifts changes the current directory), `.` and `..`, names compared without case. A file is found again on each read as the SDK finds it, by the disc offset its open stored in the 60-byte file info (+0x30; the length is at +0x34).

- **The drive takes time** (2026-11-21): an asynchronous read's callback arrives as an interrupt after the time the console's drive would take: one request at a time, each 10 ms of access plus its bytes at 8 MB/s (APPROX: of the order of a DVD drive's; no measurement of the Wii's). Until then the command block is busy and `DVDGetDriveStatus` says so. The game depends on it: its `CFileManager` frees a file slot in the read's callback (`dvdCallbackArcImpl`), but an archive keeps the slot's address until it has been decompressed and `updateArc` (once a frame) marks it ready; the callback marks the *first* archive whose slot matches. With reads finishing in 1 ms, a read on a reused slot completed while the older archive still held it: the older archive was marked again and the newer never, so the scene waited for good. It happened every time at the first remix (four games' archives on five slots: a black screen with no sound, 15,887,895 bytes read). Synchronous reads still return at once (their thread would wait either way). `QILIN_DVD_TRACE=1` logs each open, read and completion.
- Bytes past a file's end are zero (the game rounds lengths up to 32; on the console they would be whatever follows on the disc).
- Cancels only change how a pending completion reports, since reads finish at once.

## GX (`recomp/runtime/gx.*`, `gx_fifo.cpp`; v0.14.0: the CPU side)

GX is replaced at its API, as the roadmap says: its own code drives the GPU's registers through pointers loaded from memory, which the runtime couldn't catch without checking every load and store. The native GX keeps the state the game's calls set up **as the API describes it** (vertex descriptors and formats, the transform unit's matrices, lighting, texture coordinate generation, TEV stages and colours, blending and depth, textures, copies), which is what the renderer will read. Until the Vulkan renderer exists, a headless sink receives the draws and copies and counts them.

- **The SDK's own defaults:** native `GXInit` calls the **lifted** `__GXInitGX`, which calls the native setters with the SDK's default arguments (it reads only constants and the SDK's default render mode, and touches no hardware). So the state after `GXInit` is the SDK's by construction.
- **Pure GX functions are lifted:** the texture, TLUT and light object functions (`GXInitTexObj*`, `GXGetTexObj*`, `GXInitTlutObj`, `GXInitLight*` …), `GXGetTexBufferSize`, `GXGetYScaleFactor`, `GXAdjustForOverscan` and `GXSetTevDirect`. They work only on what the caller passes, in the SDK's layout. The natives that consume those objects (`GXLoadTexObj`, `GXLoadTlut`, `GXLoadLightObjImm`) decode the SDK's layout, read from its getters (the texture object's size, address, format, wrap modes and mipmap flag; the TLUT's format, address and entries; the light's colour, attenuation, position and direction).
- **Numbers the game depends on come from the SDK's code:** `GXSetDispCopyYScale` returns the frame buffer's line count by the SDK's arithmetic (ported instruction by instruction); `GXSetTevOp` takes its presets from the SDK's own tables in the game's data, found through `GXSetTevOp`'s instructions and checked at first use; `GXClearVtxDesc` leaves the position direct, as the SDK's does.
- **The FIFO:** lifted code writes vertices straight to the write-gather pipe (`0xCC008000`) where the SDK's inline vertex functions were compiled into it: 322 stores in 12 functions (NW4R's quads, lines and glyphs, the Home Button Menu, the Mii library, a few of the game's own). The lifter turns exactly those stores (found by `hwaccess`'s constant propagation) into `rt::fifo_st8/16/32` calls, and `stfs`/`psq_st` there into the same with their conversions; every other store stays a plain memory store. Native `GXBegin` opens a draw, the stores append its vertex bytes, and the draw goes to the sink when its vertex count has arrived. `GXCallDisplayList` walks a display list's draw commands. FIFO data outside a draw, or any command other than a draw, a NOP or a vertex-cache invalidation, stops with its value: nothing in the game needs one yet. In the differential test these calls stop with a memory fault, as the original does under Unicorn, so its results are unchanged.
- **Vertex sizes** follow the descriptors and formats: matrix indices a byte each, indexed attributes one or two bytes (three indices for NBT3 normals), direct ones by their component count and type; a component type GX doesn't define stops.
- **Not modelled yet, and saying so:** fog range adjustment (stops if enabled), the 16-bit depth formats' scale and offset, performance metrics, the bounding box, and CPU access to the embedded frame buffer (the `GXPoke*` state is accepted; a peek would stop as an unregistered function).

## VI (`recomp/runtime/vi.cpp`)

`VIConfigure` records the render mode; `VISetNextFrameBuffer`, `VIFlush`, `VISetBlack` and the pre- and post-retrace callbacks are kept. **The retrace** is a periodic interrupt at the console's field rate (59.94 Hz in the 60 Hz setting, 50 Hz otherwise), run as the SDK's retrace interrupt runs: the pre-retrace callback, the flushed frame buffer goes on screen, the post-retrace callback, then the threads in `VIWaitForRetrace` wake. `VIWaitForRetrace` sleeps on a thread queue in guest memory through the lifted `OSSleepThread`, so other threads run meanwhile. A late retrace runs once, and the next is a period after it: the game never sees a burst of retraces after a stall.

## The host side: window, renderer, audio, keyboard (after v0.15.0)

`qilin_run` now opens a window (SDL3) and draws with Vulkan 1.3; `QILIN_HEADLESS=1` runs without one, as before (tests, long scripted runs), and `-DQILIN_HEADLESS_ONLY=ON` builds without SDL, Vulkan or glslang at all. Third-party code is fetched at configure time, pinned by SHA-256, never committed: SDL3 3.4.20 (zlib; a system SDL3 is used if found), Khronos' Vulkan headers 1.3.299 (Apache-2.0; the Vulkan loader comes through SDL, so no Vulkan SDK is needed) The shaders' SPIR-V is committed beside their GLSL (`recomp/runtime/shaders/spirv`, our own code compiled) with a stamp of the GLSL's SHA-256 (line endings normalised): a configure stops if they drift apart, and `-DQILIN_BUILD_SHADERS=ON` fetches glslang 16.6.0 (BSD-3/Apache-2.0) to regenerate them. A default build needs only SDL3 and the Vulkan headers.

- **Threads:** the window and its events stay on the main thread (macOS requires it); the game runs on its own host thread. Vulkan is used from whichever guest thread draws (one at a time: the run token).
- **The renderer** (`gx_vulkan.cpp`, the GX `Sink`): GX's transform unit runs on the CPU per vertex (position and normal matrices from GX's matrix memory, perspective or orthographic projection into GX's clip space, z/w from −1 at near to 0 at far, mapped to Vulkan's 0..1; the two colour channels with GX's lighting, spot or no attenuation; texture coordinate generation from positions, normals or texture coordinates through 2x4/3x4 matrices, per-vertex matrix indices, the post-transform stage, SRTG). The GPU gets clip-space vertices as triangle lists (quads, strips and fans expanded); `shaders/gx.frag` interprets the TEV stages in GX's integer ranges (8-bit inputs, 11-bit signed registers, compare ops, swap tables, konst selections) and the alpha compare. Blending, write masks and the three blend modes are pipeline state (one pipeline per combination, made on first use); viewport, scissor, culling and depth are dynamic state. The EFB is a 640x528 RGBA8 + D32 image; `GXCopyDisp` blits its source rectangle to the window at the console's aspect (16:9 with the widescreen setting), presents (mailbox if available), and clears the EFB rectangle if asked.
- **Textures** (`gx_texture.cpp`): I4, I8, IA4, IA8, RGB565, RGB5A3, RGBA8, C4, C8, C14X2 (TLUTs IA8, RGB565, RGB5A3) and CMPR decoded to RGBA8 from GX's tiled layouts; cached by address, format, size and TLUT, re-checked once a frame by a hash of the texel (and TLUT) bytes.
- **Copies to textures** (`GXCopyTex`, `shaders/copy.*`): the EFB's rectangle into an RGBA8 image keyed by the destination address, converted as the copy format says (RGB, intensity as BT.601 luma, single channels, RG/GB read as IA8), halved by a 2x2 box with the mipmap flag; the next texture at that address with that size uses it, unless the CPU has since written the bytes there (a hash taken at copy time). The copy stays on the GPU: guest memory isn't written (nothing seen reads it back yet). Depth and YUV copies stop.
- **Mipmaps and LOD:** every level the texture object allows (its maximum LOD, at most down to 1x1) is decoded and uploaded; the sampler takes the filters, LOD range and bias from the object's mode words, read from the SDK's `GXInitTexObjLOD` (mode0: wraps bits 0-3, magnification bit 4, minification hardware code bits 5-7 from the SDK's table 0,4,1,5,2,6, LOD bias x32 bits 9-16; mode1: minimum and maximum LOD x16).
- **Lines and points** become screen-space quads: a line widened across its minor axis by its width in sixths of a pixel, a point a square of its size; neither is culled.
- **Fog:** GX's model in the shader: depth from 0 at the viewport's near to 1 at its far, the distance into the fog A/(B-z)-C (perspective) or A*z-C (orthographic) with A, B, C from `GXSetFog`'s start, end, near and far, then the linear, exponential, squared-exponential or reverse curves; mixed toward the fog colour.
- **Manual texture-coordinate scaling** (`GXSetTexCoordScaleManually`): coordinates scaled by the game's s/t scale instead of the texture's size.
- **Stops (not drawn yet):** indirect texturing that changes coordinates, bump-map texture coordinates, specular lighting, normals with binormals and tangents, logic ops other than copy, Z textures, depth or YUV copies to textures, a scissor box offset. **APPROX:** the TEV's rounding and konst fractions, CMPR's in-between colours, edge LOD, anisotropy, cylindrical wrapping, line and point texture-coordinate offsets, fog's fixed-point steps, destination alpha with blending, the EFB's pixel format (always RGBA8).
- **Input reaches the game:** traced through KPAD into the game's `CController` (buttons held during each scripted press); its input-check manager tests the D-pad, Home, +, -, 1, 2, Z and C by mask, and A through each registered checker's timing window (the rhythm engine's judgement).
- **Audio:** what AI plays goes to the default output device at 32 kHz through an SDL audio stream, **held at a set depth** (`[audio] latency_ms`, 10 ms by default, raised to the device's floor; `host.cpp`'s audio clock). The game's DMA runs by the time base, the sound card by its own crystal, so left alone the queue wanders and clicks. The device stays paused until the queue reaches the target; then every 48 ms SDL's resampling ratio is set to the game's speed times 1 + 1% of the relative error of the queue's depth averaged over about 200 ms, clamped to ±0.5%. A queue found empty is refilled to the target with silence at once (an underrun, counted); frames arriving beyond the target plus 40 ms (a catch-up burst after a stall) are dropped, counted. The device buffer is asked for 128 samples (SDL then uses WASAPI's low-latency shared mode, `IAudioClient3`, which a driver grants down to its own minimum). The device takes a whole period at each read, so the queue can be held no lower than a period plus 4 ms (the game's 3 ms frames and their jitter): `open_audio` computes that floor and raises a lower setting to it, saying so. Measured (Windows, a USB interface with a 10 ms period, 40 s at the title): the floor 14 ms, 14.2 on average, 4.7–23.0, no underruns, ratio 1.00007 (at the earlier 30 ms: 30.5 on average). Lower would need WASAPI's exclusive mode (3 ms on the same device), which SDL doesn't offer. The run report prints these.
- **Keyboard as the Wii Remote** (held upright): A = A, Right Shift, Right arrow or Space; B = B, Left Shift or Left arrow (the pairs for two hands, right A and left B as on a controller's shoulders); 1, 2; + = Enter; − = Backspace or Tab; Home = H; the D-pad = I, J, K, L or the Up and Down arrows. A remote is connected whenever there is a window (or a `QILIN_INPUT` script); the two add up.
- **First run** (GTX 1080 Ti, Windows): 60 s windowed with A pressed from 24 s: 3,581 frames presented, the title's music and voices through the speakers, no stop.

## The player's side: settings, window, controllers, enhancements (after v0.16.0)

As in the other Qilin recomps (`docs/naming.md`): the window is named after the game and opens at the largest whole multiple of the picture (854×480 at 16:9, 640×480 at 4:3) that fits nine tenths of the main display; F11 or Alt+Enter switch borderless fullscreen. The data folder is `<per-user data>/qilin/beatthebeat` (`settings.cpp`'s `game_data_dir`; an old `BeatTheBeat-QilinComp` folder, the project's former name, moves there once).

- **The settings file** (`settings.*`, `beatthebeat.ini`): `[display]` has the preset (`original`, `low-end`, `desktop`) and the keys that override it; `[console]` the Wii's own settings, which `console.hpp` hands to the SC and VI natives. `parse_settings` is apart from the file, and unit-tested; a malformed line ends the start with the file, line and reason.
- **Controllers** (`host.cpp`): SDL's gamepad API, hot-plugged; the first controller plays the Wii Remote held upright, merged with the keyboard. `WPADControlMotor` rumbles it (through an SDL user event, so the main thread does it).
- **Internal resolution** (`internal_scale`): GX's coordinates stay in EFB pixels; the renderer multiplies them where they meet the images (the EFB, viewports, scissors, clears, the display blit, texture copies, which keep the resolution, and the statistics' readback). Line and point widths follow, being computed relative to the viewport.
- **Anisotropic filtering** (`anisotropy`): on samplers that filter linearly, within the GPU's limit; a GPU without it says so and filters as the console does.
- **vsync**: on, mailbox (no tearing, presenting never waits, three images) or FIFO (two images: each further one is a refresh of lag); off, immediate where there is one. The log names the mode.
- **Exclusive-mode sound (Windows, `wasapi.*`, `[audio] exclusive`, on by default):** the default output through WASAPI's exclusive mode at the device's minimum period, event-driven, on its own thread in MMCSS's "Pro Audio" class. The format is the first the device takes exclusively: 48 kHz, then its own rate, then 44.1, 96, 88.2 and 192 kHz; float, 24 bits in 32, 32 and 16-bit samples. SDL still converts and resamples: `open` makes an SDL audio stream with no device (32 kHz 16-bit stereo in, the device's format out), the host's audio clock puts into it and sets its ratio as before, and each period the thread takes a period's worth, silence where the stream is short. Exclusive mode bypasses Windows' volume and mute: unless the endpoint does volume in hardware, the thread applies the endpoint's level (dB to linear) and mute as the stream's gain, read every 128 periods. The device unavailable (another program exclusive, no format) falls back to the shared mode; the device lost (unplugged, the default changed) makes the main loop open the output again. Measured (a USB interface, 48 kHz, 24 bits in 32, 3 ms period): the floor 7 ms, 7.3 on average over 60 s, 3.2-18.2, no underruns; 8 frames dropped at start-up (the display's mode switch).
- **The vblank lock** (`gx_vulkan.cpp`'s `steer_to_vblank`, Windows): with the display lock on, after each present the time to the next vblank (the slack, from `DwmGetCompositionTimingInfo` through `machine.cpp`'s `display_vblank`, on the steady clock) is compared with a target of 1 ms plus four standard deviations of its spread, at least 3 ms (the GPU and the compositor's latch). Its error, wrapped to half a refresh either way, is averaged over about a quarter of a second, and a PI loop (Kp 1/s, Ki 0.25/s², well damped, settles in about 10 s) sets the game's speed within 0.2% of the display lock's: presenting early slows the game a little. Frames after a long gap (loading, the menu) restart the averages. At 2.5 ms about one frame in 500 just missed its vblank; at 3 ms none in 60 s (120 Hz, GTX 1080 Ti: 3.08 ms on average, spread 0.17 ms, steered by 0.004%). The run report prints these. Elsewhere there are no vblank times, and the display lock alone runs.
- **What each kind of display gets** (all set at start): a refresh that is a whole multiple (1-8) of the game's 59.94 Hz within 0.5%, or in the PAL 50 Hz setting 50 Hz itself (no multiples: the owner's choice): the display lock, and on Windows the vblank lock. A desktop refresh that isn't (75, 144, 165 Hz): fullscreen switches to the highest mode at the same resolution that is (`match_refresh`), windowed play is uneven and says so. **Variable refresh** (`variable_refresh`, off by default, for G-Sync, FreeSync or VRR on in the driver; no program can see that setting): no lock, no mode switch, the game at its own rate and FIFO presenting, which variable refresh follows (mailbox can hold a driver to the fixed rate), with two images, so a frame is shown at once and presenting never waits at 60 frames a second. Measured on a 144 Hz desktop: 0.1 ms per present, sound at 7.1 ms. Whether the display really followed needs the driver's indicator (NVIDIA: the G-SYNC indicator).
- **Locking to the display** (`lock_to_display`, with vsync; set at start, `host.cpp`): when the display's refresh (SDL's exact rational where it has one) divided by 1-8 (in the 50 Hz setting, only by 1) is within 0.5% of the field rate, the time base runs at that ratio (`set_time_base_speed`: each setting a new entry in a ring of 256 that readers on any thread take whole, anchored so the clock doesn't jump, and the clock clamped never to go back), so the retrace comes at the display's rate and no frame is shown twice. Sound follows (the audio clock's ratio starts from the same speed). Not for hidden or bot runs (they must replay alike). **`match_refresh`**: when the desktop's refresh can't lock (75 Hz, 144 Hz), fullscreen uses an exclusive mode at the desktop's resolution with the highest refresh that can (`SDL_SetWindowFullscreenMode`); a 75 Hz 3440x1440 display with a 120 Hz mode goes to 120 Hz, each frame shown twice. Windowed play keeps the desktop's rate and says so.
- **The picture in the window:** each display copy goes to a kept image (`last_frame`), and every presented frame scales it into the window: whole multiples of 854×480 or 640×480 (the sharpest; fit where the window is smaller), the largest that keeps the aspect, or the whole window; filtered or nearest (`smooth`).
- **The settings menu** (`menu.*`, Dear ImGui with its SDL3 and Vulkan backends, dynamic rendering into the window's images after the picture):
  - **Pausing** (`pause.*`): the main thread asks; the game's thread parks at the end of `copy_display`, the one place where the renderer holds nothing half-recorded. It parks holding the run token, so no guest thread runs. The time base skips the paused span (`skip_time_base`), so the game's clock, its alarms and the audio clock carry on where they left off; `QILIN_RUN_SECONDS` counts game time.
  - **While parked** the main thread owns the renderer: `present_paused` shows the last picture with the menu over it (vsync paces it). On closing, `apply_display_settings` waits for the GPU and remakes what changed: the EFB images at a new internal resolution (texture copies made at the old one are remade when next copied), the samplers for anisotropy, and the swapchain for vsync.
  - **ImGui's frames** are built on the main thread and drawn by whichever thread owns the renderer, under one lock (the start-up hint is drawn by the game's own frames).
  - **Verified** by driving the real window with mouse clicks (Windows, GTX 1080 Ti): changing the picture size, vsync and 3× resolution, then closing, saved the file and the game carried on at 1920×1368 with the same picture.
- **Matched to Punch-Out's menu (2026-11-20):**
  - **Close and Quit** at the top right of every page.
  - **Bindable controls:** each of the Wii Remote's buttons (`Control`, settings.hpp) has a list of `Binding`s: a controller button (`PadButton` bits, by an Xbox pad's names; the left stick past half way is the d-pad, the triggers past half way are buttons), a key (SDL's scancode name, so the same place on any layout) or the mouse's left button. The file keeps them as `a = pad:A, pad:RB, key:A, ...` in `[controls]`; a malformed or reserved input (Escape, F1, F3, F11) stops at start with the line. `host.cpp` compiles them into a key table and a per-bit table when they change (`rebuild_controls`), so a key or button costs a lookup. The menu sets one by pressing it: Add, then the next key (Escape cancels), controller button or click within 6 s; an input taken from another button moves and says so; clicking one removes it.
  - **F3, frame times** (`performance_overlay`): the render thread records the time between presents (20 s at 60 a second, under a lock); the readout shows the frame rate and average, the 1% and 0.1% lows (the frame rates of the slowest 1% and 0.1% of frame times), the worst frame, a graph, the display's refresh and how many times each frame is shown, how long before its vblank a frame is presented, and the sound's queue.
  - **The CRT look** (`look = crt`, `scanlines`, `mask`): `finish_frame` draws the last picture into the window's image through `shaders/crt.frag` (a full-screen triangle, `present.vert`) instead of blitting it: the console's raster lines as Gaussian beams whose height grows with brightness, with gaps that fade where a line has fewer than about two window rows, and an aperture grille's stripes a window pixel wide, in linear light (2.4). The pipeline is made on first use for the window's format.
  - **"Look at the picture"** hides the menu until a key, click or button.
  - **Internal resolution "Auto"** (`internal_scale = 0`): the whole number of times 480 lines fit the display's height in pixels, 1-8.
  - **The display's mode and the locks follow full screen** (`apply_display_mode`): at start, on entering or leaving full screen, on the window's display or its mode changing, and when the menu's refresh settings change, the fullscreen mode is chosen again (set only if it differs, since setting it switches the display and comes back as a mode-change event), the clock is locked to the refresh or released (speed 1), and the vblank lock follows (`lock_frames_to_vblank(0)` is off). Before, this happened only at start, so F11 into the 120 Hz mode left the game unlocked.
- Not done yet: MSAA, widescreen beyond 16:9.

## Efficiency (after v0.16.0)

`QILIN_PROFILE=1` reports the process's CPU time against the wall clock, the time in draws (texture checks included), presenting frames and the mixer, what's left (lifted code, the OS), and each renderer ring's peak use in a frame. Measured at the title (45 s, A pressed four times; Windows, a desktop CPU and a GTX 1080 Ti):

| Build | Windowed | Headless |
|---|---|---|
| Checked memory (the default, for bring-up) | 16% of one core | 15% |
| `-DQILIN_RUNTIME_CHECKED=OFF` | 12% | 8% |
| `-DQILIN_LTO=ON` as well | no measurable change | no measurable change |

- **Textures follow the console's coherency rule** (`coherence.*`). The GPU sees what the CPU wrote only once the game flushes or stores the range (`DCFlushRange`, `DCStoreRange`, lifted `dcbf`/`dcbst` through `rt::cache_store`) or DMA writes it (disc and NAND reads). Each such write stamps the 4 KB pages it covers with a generation; a texture or EFB copy is re-checked only when a page under it has a newer stamp, then hashed once, and decoded again only if its bytes really changed. A game that skips the flush gets stale data on the console too. Before, textures were re-hashed every draw: 102 µs a draw, 61% of a core in all; now 0.3 µs.
- **The renderer's rings grow instead of being sized for the worst case:** vertices, uniforms and uploads start at 1, 1 and 8 MB per frame in flight, with 1,024 descriptor sets a pool; a frame that needs more spills into extra buffers and pools, and its slot gets one buffer of the size it needed when it comes round again. Peaks at the title: 113 KB of vertices, 181 KB of uniforms, 4 MB of uploads (start-up's textures), 132 sets. Host-visible memory reserved: about 20 MB, from about 210 MB; it matters on boards whose GPU shares the CPU's memory.
- **Lifted loops** take the slow path only when an interrupt is due now, not whenever an I/O completion is queued (v0.16.0's fixes).
- **Players** should build with `-DQILIN_RUNTIME_CHECKED=OFF`, as the installer now does by default (`-Checked` for the checks): checked memory is for bring-up (its stops name each unexpected access) and costs about half the lifted code's time. Unchecked, an access outside guest memory faults instead of stopping with a report.
- **A switch wakes one thread:** each guest thread's host thread waits on its own condition variable (one shared one woke all 13 waiting threads on each of ~900 switches a second): about 9% less CPU.
- **The TEV shader is specialised per configuration** (`shaders/gx.frag`): the stage count, each stage's inputs, ops, order and selections, the swap tables, the alpha compare's functions, the fog type and the manual-scaling flags are specialisation constants (ids 0-68, `Spec` in `gx_vulkan.cpp`), so the driver folds every selector away and compiles straight-line code; registers, konst colours, reference values and fog parameters stay in the uniform block. A pipeline per (blend state, configuration): 10 at the title. Measured with GPU timestamps (`QILIN_PROFILE=1`, a GTX 1080 Ti): 2.18 ms a frame interpreting the stages, 0.61 ms specialised; an experiment with a trivial shader gave 0.37 ms, so the interpreter was about 80% of the GPU's work.
- **The pipeline cache is kept** in the per-user folder (`pipelines.bin`, written every 5 s when new pipelines were made, through a temporary file; used only if its header names this GPU and driver). First use of a configuration compiled in 45 ms with no cache, 0.1 ms with it: on a slower GPU, the difference between a stutter and none.
- **Pipelines are made ahead:** every configuration made is listed in `pipelines.keys` (magic `QPK1`, the word count per key, then the blend word and 69 specialisation constants per key), written with the cache. At start a background thread makes them all (`build_pipeline` reads only start-up's shaders and layout, and Vulkan synchronises the cache); `pipeline()` takes them from there on first use. 20 in 2 ms at the title on a GTX 1080 Ti, and no compile in the frame. A configuration never met before still compiles when first drawn: the TEV shader is specialised, with no general one to draw it meanwhile.
- **Windows' scheduling:** the idle wait (`interrupts.cpp`'s `idle_wait`) sleeps on a high-resolution waitable timer (Windows 10 1803 on) or an event that posting sets, not a condition variable's timed wait, which rounds to the timer period. `fine_timers` also opts the process out of power throttling (EcoQoS, and Windows 11's ignoring `timeBeginPeriod` for a window that isn't visible), and every host thread that runs guest code joins MMCSS's "Games" class (`game_thread_started`).
- **The render thread** (`gx_vulkan.cpp`, "the render thread"): the game's thread keeps everything that reads guest memory or decides (vertices transformed, textures checked and decoded into the upload ring, images made, pipelines chosen, batching, the rings); everything that records or submits runs on a render thread from an in-order queue of closures (`record`, handed over 64 at a time and at each frame's end): descriptor sets, draws, upload copies, clears, EFB copies, acquire, submit, present and the vblank lock. Ownership: rings, texture and copy maps, image creation, the garbage list and samplers are the game side's; command buffers, descriptor pools, the rendering state (`r_` functions, `g_rec`) and the swapchain the render thread's. Texture uploads go from UNDEFINED (every level is rewritten) and copies to textures from UNDEFINED or SHADER_READ, so no layout is tracked across the threads. Before reusing a frame slot the game side waits until the render thread has submitted that slot's last frame (`wait_submitted`), then its fence; images are freed after that, as before. The queue is drained before the menu parks the game, before the main thread's paused frames and display changes, and for the lockstep bot. An exception on the render thread is kept and rethrown on the game side at its next hand-over. The render thread has the game's threads' scheduling class (MMCSS "Games"): at normal priority its presents spread by 2 ms and missed vblanks. Measured over 40 s at the title: the game's thread 9.8% of a core where it was 11.6%, the process 20.6% against 19.3%; frames identical to the build before.
- **Draws are batched** (`gx_vulkan.cpp`'s `Batch`): consecutive draws with the same pipeline, textures, uniform block and dynamic state, their vertices adjacent in the ring, are one `vkCmdDraw`; the batch is flushed in `end_rendering` (texture uploads, copies and the frame's end pass through it) and before an EFB clear; state a rendering pass already has isn't set again. 1.28 million draws in 0.72 million batches over 45 s; 1.0 µs a draw where it was 1.7; dumped frames identical to the unbatched build's.
- **The sampling profiler** (`QILIN_SAMPLE=1`, Windows, `profile.cpp`): every millisecond each other thread is paused (`SuspendThread`), its instruction pointer read and the thread let go; nothing is allocated while one is paused (the heap's lock). At the report, DbgHelp names the addresses (a build with `-DQILIN_DEBUG_SYMBOLS=ON`: `/Zi`, `/DEBUG /OPT:REF /OPT:ICF`, the same optimised code), time waiting in the OS (ntdll's and win32u's waits, the window's `GetMessage`) is counted apart, and the 60 hottest functions are listed as shares of the busy samples. At the title (2026-11-20, after the fixes below): 0.18 threads busy; the PowerPC floating-point helpers lead (`fmas` 7.7%, `quantize` 3.6%, `fmuls` 3.3%, `dequantize` 2.9%, `stfs` 2.5%: the exactness checks the console's results need), then the driver and the renderer's draws.
- **Native calls check for interrupts on every 16th call** (or at once when one is queued): reading the clock at each was 7% of the game's CPU. **NaN, infinity and sign tests are bit tests** (`is_nan`, `is_inf`, `sign_bit` in `guest.hpp`): MSVC's `std::isnan`/`std::isinf` are calls into the C runtime (`_dclass`, 3%).
- Still to measure on a Pi 4-class board: the GPU time per frame (the profile prints it), and the first run's compiles. An estimate from the PC (2026-11-20): the game's threads take turns as on the console's single core and need about 0.18 of a desktop core, which a Pi 4's Cortex-A72 (roughly 5 to 8 times slower a core) may not keep up with at full speed. Next: drawing on its own thread (about a sixth of that time), then the hottest helpers.

## Input: a scripted remote (`recomp/runtime/input.*`, after v0.15.0)

## The lockstep test bot (`recomp/runtime/bot.*`, `tools/bot/`)

Fixed-time scripts can't play this game past its calibration: the game's beat starts at a slightly different moment in each run, so presses timed from start are in or out of time by chance. `QILIN_BOT=1` puts the runtime in lockstep with a bot on its standard input and output (`bot.hpp` has the protocol):

- **Each frame's end** (the renderer's display copy) sends the frame number, the game's clock, the picture scaled down to 160x114 and the audio played since the last frame, each AI frame with the clock at which it started (by the DMA's own schedule, not the interrupt's delivery). The runtime then waits for the bot's answer: presses, each from one moment of the game's clock to another, which `input.cpp` makes exactly then (WPAD's reports are 5 ms apart).
- **The game's clock stops** while the runtime waits for the picture and the bot (`skip_time_base`, as the settings menu's pause): a slow bot or a busy computer changes nothing the game sees. Runs are close to deterministic: twelve 30 s runs read exactly the same bytes and drew within 0.2% of the same number of times.
- **The bot** (`tools/bot/qilinbot.py`, standard library only) starts the runtime hidden, finds onsets in the game's own audio with the game's clock, fits the beat by least squares (period right to 0.02 ms on jittered onsets with gaps and strays), ignores the sounds of its own presses (they had steered its beat), keeps a watchdog (no new picture or sound for 30 s: stalled, with the runtime's report and the last picture kept) and saves a picture every few seconds. `tools/bot/beatthebeat.py` is this game's plan: it recognises screens from measured features of the picture, presses through menus and dialogue (A and B together where the tutorial shows the remote), puts presses on the heard beat, and in the countdown reads the digits from their strokes (an oval "0" has strokes at both edges in most rows) to press on the zeros. Its pictures and logs are game-derived: scratch only.

## Audio (`recomp/runtime/audio.cpp`; v0.15.0)

**AX is lifted whole** (its eight units: voices and priorities, the setters, PB sync, aux callbacks, each frame's command list): it is CPU code with no hardware access, and NW4R's sound system and the Home Button Menu write AX's voice structures directly, so whatever runs the voices must read the SDK's own structures. Native: **AI** (the audio DMA) and **the DSP**.

- **The protocol is AX's own**, read from its code: AX registers a DSP task (microcode, memory, four callbacks) and spins until the task's init callback has run, so `DSPAddTask` runs it before returning. Each **AI DMA interrupt** (every 96 stereo samples at 32 kHz: 3 ms, a periodic interrupt) calls AX's `__AXOutAiCallback`, which, if the DSP is idle, builds and sends the next frame: mail `0xBABE0080`, then the command list's address (the list built the frame before), and queues the next of three 384-byte output buffers. When the DSP has finished a frame, the task's resume callback runs (an interrupt), and AX either starts the pending frame or marks the DSP idle.
- **The command list** is 16-bit words, each command followed by its arguments, addresses in two halves: command 0 (the studio parameters), 1, 2 or 3 by output mode (the mix buffers), 4 (the first voice parameter block), then aux and output commands.
- **The command list in full** (from `__AXNextFrame`): 0 studio; 1/2/3 mix buffer by output mode (0 stereo, 1 surround, 2 Dolby Pro Logic II); 4 first PB; 5/6/7 aux A/B/C (return volume, input buffer, output buffer); 8/9 aux A/B for DPL2 (six buffers); 10 compressor (0x8000, a value, a table); 11 output (master volume, mix buffer, the AI buffer) or 12 for DPL2; 13 the four remote speakers' buffers (18 samples a frame, 6 kHz); 14 end.
- **The PB** (the DSP's copy, 320 bytes; AX's `__AXServiceVPB` copies the CPU's changes in by sync bit, and with none copies state, volume and position back): next +0, resampler type +8, mixer control +12 (32 bits), state +16, mix +20 (12 pairs of volume and per-sample change: L, R, aux A L/R, B L/R, C L/R, S, aux A/B/C S; NW4R's `SetVoiceMix` gives the enable and ramp bits), interaural delay +68, depop +82, envelope volume +106 and per-sample change +108, loop flag +110, format +112 (0 ADPCM, 0x0A PCM16, 0x19 PCM8), loop/end/current address +114/+118/+122, ADPCM coefficients +126, gain +158, predictor/scale +160, history +162/+164, resampling ratio (16.16) +166, fraction +170, four history samples +172, ADPCM loop context +180, one-pole low-pass +186 (on, y, b0, a1 with b0 = 32767 − a1, from `AXGetLpfCoefs`), biquad +194, remote +214. DSP addresses are physical: nibbles for ADPCM, bytes for PCM8, samples for PCM16 (NW4R's `GetSampleByDspAddress`). Volumes: 0x7FFF is 1.0 (NW4R scales by 32767); NW4R spreads every change over a frame's 96 samples.
- **The mixer** carries this out each frame. Exact (what game logic sees): positions, loops and ends (state 0 when a voice without a loop passes its end), DSP-ADPCM with its history and loop context, envelope and mix ramps, aux round trips (the bus to AX's input buffer, the callback's output from an earlier frame mixed back at the return volume), and the write-back. APPROX: the polyphase resampler (a Catmull-Rom cubic: its tables are in the DSP's ROM), rounding, and the compressor (saturation). Stops: biquad, interaural delay, AX's Pro Logic I mode (this game never uses it), sample data outside MEM1/MEM2.
- **Dolby Pro Logic II** (the console's surround setting: the game maps SC's surround to NW4R's DPL2). The layout is exact, from the game's code: the main bus and aux A and B carry L, R, Ls and Rs; a voice's Ls goes in each bus's S slot and its Rs in aux C's slots (C-L main, C-R aux A, C-S aux B: `CalcMixParam`), so aux C doesn't exist in DPL2; commands 8 and 9 hand aux A and B over as L, R, Ls with Rs from its own pointer, and take each output channel from its own pointer (`__AXGetAux*Dpl2`: three 1536-byte buffers a bus, four channels of 96); command 12 outputs. **APPROX:** the encoding into two channels (`dpl2.hpp`): the published matrix Lt = L − j(0.8718 Ls + 0.4899 Rs), Rt = R + j(0.4899 Ls + 0.8718 Rs), the 90-degree shift by two all-pass chains of this project's own design (`tools/analysis/design_dpl2_allpass.py`: unity gain everywhere, within 1.4° of 90° from 20 Hz to 15 kHz). Unit-tested against the matrix (levels at 60 Hz, 1 kHz and 12 kHz, the phase relations). The game plays through to its opening scene in either mode, with no clipping.
- **Stereo has no main S channel**, from `__AXNextFrame`'s own DSP cycle budget: the set-up commands 1, 2 and 3 (stereo, surround, DPL2) cost 733, 829 and 925 cycles, one more 96-sample channel each (L R; L R S; L R Ls Rs), while the output command (11, 1172) and the aux commands (5/6/7, 2235) are the same for stereo and surround. So in stereo, what reaches S isn't heard. It does reach it: NW4R runs AXFX's reverb with L, R and S buffers in every mode but DPL2 (`FxReverbHi::UpdateBuffer`), so its surround return arrives in stereo (found 2026-11-19, just past the title, where the game had stopped on it). The remote speakers get silence. The AI buffer is written L then R (the order to confirm when there is host output). `QILIN_AUDIO_DUMP=<file.wav>` writes what AI plays: the title's music comes out at sensible levels with nothing clipped.

## NAND (`recomp/runtime/nand.*`; v0.15.0)

The game's saves in a host folder laid out as the flash's own paths (`<root>/title/00010000/534f4d50/data/...`; the title's code from the disc ID). The root is `QILIN_NAND`, or the platform's per-user data folder (`%LOCALAPPDATA%\qilin\beatthebeat\nand`, `~/Library/Application Support/...`, `$XDG_DATA_HOME` or `~/.local/share/...`): never the repository, since saves are the game's data. The title's data directory and `/tmp` exist before the game runs, as a console's system makes them.

- Paths: absolute as given, relative from the title's home directory; `..` is refused (it would leave the folder).
- Results as the game's backup manager tests them (read from its code): `NANDGetType` -12 for "no save yet", `NANDCheck`'s answer bits (5: no space, 10: too many files; 0 here), `NANDGetStatus` as an existence check (owner and group aren't kept; the permission is owner read/write, as the game creates its files), `NANDMove` failing with EXISTS onto an existing file, as on the console.
- Files: create, open (by the address of the game's file info), read, write, seek, length, close. The first boot writes `/tmp/Riq.dat` (2,592 bytes, with a CRC-32 from the lifted `OSCalcCRC32`), moves it home, and writes the save banner (`NANDInitBanner` lifted).
- Asynchronous requests: accepted at once, their result through the callback 1 ms later. A safe open for reading is a plain open; **for writing** (the SDK's copy-and-commit) it isn't modelled yet and stops. The **Mii database** (`/shared2/menu/FaceLib/RFL_DB.dat`) is the console's, not the game's: the folder has it only if the owner copies in their own; without it the Mii library gets NOEXISTS and goes on, as on a console without one.

## Memory: the arenas (v0.15.0)

The game makes one heap of the whole MEM1 arena and one of the MEM2 arena (`memInitHeap`), so the arenas' bounds are its heap sizes. With `OSInit`'s fallback end the MEM1 heap was 480 KB short, and the game said so itself (`Can't Alloc Heap: Required 749120 B, Free 271088 B`). **MEM1's arena now ends where a console's apploader puts the disc's file table**: the top of MEM1 less `sys/fst.bin`'s size, rounded down to 32 bytes (`0x817ED8C0` for this disc), and the runtime's 64 KB guest scratch lives in the table's place (the game doesn't read the table there: DVD is native), so the game's heap is the console's size. Still to confirm with a Dolphin dump (`lowmem.py`).

## Other native pieces

- **The locked cache** (`LCEnable`, `LCDisable`, `LCQueueLength`): a 16 KB scratchpad filled by DMA. NW4R turns it on and off, but no lifted code addresses it (nothing outside the replaced libraries builds `0xE000xxxx`; only the debugger stub touches the DMA registers), so there is no DMA, and an access would stop under checked memory.
- **SC** (`SCInit`, `SCCheckStatus`, and the settings: progressive scan, 60 Hz, aspect, language, sound mode): the settings are the runtime's, so there is nothing to load.
- **Guest scratch** (`guest_alloc` in `machine.*`): 64 KB OSInit keeps back from the top of the MEM1 arena, for the runtime's own objects the game's code works on (GX's FIFO object, VI's thread queue).

### Console settings (`recomp/runtime/console.hpp`)

The game picks its video mode from the console's settings (SC) and VI: 480p when progressive scan is on and the cable allows it, otherwise interlaced by TV format and the 60 Hz setting; 4:3 when the aspect setting is 0; its language folder from the language. On a Wii these are the owner's system settings. Here they are the runtime's, until the settings file exists: 60 Hz (EuRGB60), progressive, 16:9, English. **Compare with Dolphin only with the same settings on both sides:** they decide 50 or 60 Hz.

### To confirm: what the loader hands `OSInit`

`OSInit` takes the arenas from low memory, which IOS and the apploader fill in before the game starts. Nothing in the DOL says what they put there, so these come from `OSInit`'s own code and need confirming against the original game in Dolphin, the reference:

| Value | Now | From |
|---|---|---|
| MEM1 arena start | `0x803E94A0` | `OSInit`, when low memory gives no start: the end of the debugger stack after the main stack, rounded up to 32 bytes |
| MEM1 arena end | `0x81730000` | `OSInit`'s default when neither low memory nor the boot information gives one. A console gives one (the start of the disc's file table), so this is on the small side |
| MEM2 arena start | `0x90000800` | `OSInit` raises a lower start to this |
| MEM2 arena end | `0x933E0000` | The documented start of IOS's own heap at the top of MEM2 |
| Bus, CPU clock | 243 MHz, 729 MHz | The Wii's; the time base runs at a quarter of the bus clock |

**Checking them:** in Dolphin, turn on the debugging interface, set a breakpoint at the entry point `0x80004050` in the code view, start the game, and when it stops dump MEM1 from the memory view (it writes `mem1.raw` into Dolphin's dump folder; menu names vary between versions). Then:

```sh
python3 tools/analysis/lowmem.py path/to/mem1.raw
```

It prints every low-memory word `OSInit` and `__start` read (arenas, clocks, console type, IOS version, the boot information) next to the runtime's value, and flags the ones that differ. The dump holds the whole game image, so it stays out of git (`*.raw` is ignored).

## Where bring-up stood at v0.14.0

`main` runs its whole start-up: the video mode, the file manager, the graphics manager (`GXInit` with the SDK's defaults, the display copy set up, the first frame copied out, `VIConfigure`, the first retraces), NW4R's 3D and layout libraries, the controller manager (WPAD, KPAD), and the Home Button Menu's manager, which loads its files from the disc. It stops at `AICheckInit`, where the Home Button Menu starts its sound.

**Exercised now** (v0.14.0's run): 5 files opened and 863,689 bytes read through asynchronous DVD reads, 17 interrupts (5 from the decrementer, through the lifted alarm code and `OSSleepTicks`; the rest retraces and DVD completions), 7 retraces, 1 frame copied out. Still not exercised: a switch between two threads (only one thread has slept and woken yet) and any draw.

Next: **audio** (AI, AX, DSP). NW4R's sound system (lifted) runs from AX's audio-frame callback, so AX is also the clock the game's rhythm timing follows, and it has to run at the console's rate from the start, sounding or not. Then the Vulkan renderer for GX, once the game draws.
